## #259 - the checksum defect you reported

You reported it yesterday too; #233 shipped in 8.3 and did not fix your case.

**Cause**, `ChecksumPanel.probeForSiblingOfSelectedAlgorithm`: it returned early unless a probe had
filled the field, so a checksum loaded or typed by hand blocked any re-probe; and when no sibling
file existed for the new algorithm, the old file and old checksum simply stayed.

**Why no test caught it**: `ChecksumPanelBindingTest` pinned the OPPOSITE rule - "choosing another
algorithm never overwrites a checksum the user entered". That test was rewritten, not deleted, with
the reason in its Javadoc: a checksum belongs to the algorithm it was computed with. There was also
no UI test for the flow at all; one was added, and it immediately caught a second thing - two panels
of the same name in one JVM, because both tests in the class open the tool and forkEvery forks per
class, so the lookup is now scoped to the tool's own window.

**State**: fixed. 45 binding tests green, `ChecksumPluginUiTest` 2/2 green. **PR #260**.

Two fields (`txtChecksumFile`, `txtOwnersChecksum`) had no component names at all, which is part of
why no UI test existed: they were unreachable. They have names now.
